# Архитектура ИУ3 Android

`app` связывает независимые feature-модули. Фичи получают данные через интерфейсы репозиториев и владеют подготовкой состояния своих экранов. Реализации хранения и источники скрыты в `core:data`; Android-напоминания вынесены в `core:notifications`.

Настройки Gradle вынесены в included build `build-logic`: шаблоны application/library/api/feature и подключаемые Compose/Hilt/serialization плагины. Модуль задаёт namespace и свои зависимости через `projects.*`; версии SDK и Java находятся в общем каталоге. Примеры и устройство плагинов — в [настройке сборки](build-logic.md).

## Границы модулей

| Модуль | Ответственность |
|---|---|
| `app` | Application, Activity, сборка Hilt-графа, корневая навигация и запуск внешних Android-приложений |
| `core:common` | Clock, квалифицированные dispatchers и scope уровня приложения |
| `core:model` | Неизменяемые модели, коды протокола и общие расчёты календаря, планов и напоминаний |
| `core:data-api` | `CatalogRepository`, `UserRepository`, состояние каталога; без реализаций хранения |
| `core:data` | Внутренние реализации репозиториев, источники assets/кеша/DataStore/фото и Hilt bindings |
| `core:notifications` | Планирование Android alarms, текст уведомлений, WorkManager и восстановление очереди |
| `core:designsystem` | Палитры, компоненты, изображения и общие UI-форматтеры |
| `core:navigation` | Сериализуемые ключи, типизированные аргументы переходов и внешние URI/запросы |
| `features/*` | Навигационные entrypoints, ViewModel, состояние и интерфейс конкретной фичи |

Feature-модули не зависят друг от друга и от `core:data`. Зависимость от `core:data-api` позволяет компилятору запретить доступ к источникам и конструкторам реализаций. `app` подключает `core:data` для сборки DI-графа. Профиль дополнительно использует публичные контракты напоминаний.

Такое разделение опирается на [рекомендации Android по модульности](https://developer.android.com/topic/modularization/patterns): фича объединяет связанные экраны и их состояние, data-модуль публикует репозиторий и скрывает источники. Отдельный API-модуль выбран для соблюдения этой границы на уровне Gradle; он не является обязательным требованием Android для каждого репозитория.

## Репозитории и источники

`DefaultCatalogRepository` координирует `CatalogDataSource` и `CatalogCacheDataSource`. Публичный контракт предоставляет неизменяемый `StateFlow<CatalogState>` и main-safe `suspend refresh`. Обновления сериализованы через `Mutex`; отмена корутины распространяется вызывающему коду. При ошибке загрузки остаётся предыдущий каталог с признаком офлайн. При ошибке записи кеша уже загруженные данные остаются доступны.

Текущий `StubCatalogDataSource` читает реальные встроенные JSON-ответы. Дисковое чтение выполняется на IO dispatcher, разбор ответов — на Default. Источник назван по своей роли: он не изображает HTTP API, которого у приложения пока нет. Для сервера добавляется реализация `CatalogDataSource` и меняется binding в `DataModule`; экраны и репозиторий не выбирают транспорт.

Каталог возвращается целиком, поскольку текущие ответы образуют один согласованный снимок кафедры. Авторитетное состояние в процессе хранится в репозитории; файл `catalog-v2.json` служит восстановительным кешем. Запись идёт через `catalog.pending` и rename. Здесь нет локального редактирования каталога или SQL-запросов, поэтому Room и фиктивный Retrofit-клиент не добавлены. Если появятся независимые обновления, большой каталог или локальные изменения, потребуется пересмотреть источник истины и разделение репозиториев.

`DefaultUserRepository` владеет профилем, историей и настройками. `UserPreferencesDataSource` работает только с DataStore и сериализацией, `ProfilePhotoDataSource` — только с изображением в закрытом каталоге. Нормализация профиля и согласование сброса с импортом фото находятся в репозитории; `Mutex` не позволяет завершившемуся импорту восстановить профиль после сброса.

Основание: [Android data layer](https://developer.android.com/topic/architecture/data-layer) рекомендует репозитории как вход в слой данных, отдельные источники по физическому хранилищу, `suspend` для разовых операций и Flow для наблюдения. Выбор кеша и отсутствие базы данных определены текущей моделью данных приложения.

## Зависимости и фоновые компоненты

`DataContainer`, `DataContainerOwner` и получение репозиториев через `Context` удалены. Репозитории, источники, ViewModel и фоновые задачи получают зависимости через конструкторы. Hilt хранит по одному экземпляру репозиториев на приложение; `Json` задаётся data-модулем, `Clock`, dispatchers и scope приложения — `core:common`. Android `Context` нужен источникам и платформенным адаптерам, но не ViewModel.

Hilt выбран потому, что один граф нужен нескольким feature-модулям, Application, receivers и WorkManager. [Android DI](https://developer.android.com/training/dependency-injection) описывает передачу зависимостей извне; [Hilt с Jetpack](https://developer.android.com/training/dependency-injection/hilt-jetpack) предоставляет интеграции для ViewModel и Worker. Используется Hilt 2.59.2 с поддержкой AGP 9, указанной в [релизах Dagger](https://github.com/google/dagger/releases/tag/dagger-2.59.2), и KSP. Kapt не подключён.

`IU3Application` передаёт `HiltWorkerFactory` в конфигурацию WorkManager. Стандартный WorkManager initializer удалён из объединённого manifest. Worker использует `@HiltWorker` и assisted context/parameters. `SynchronizeReminders` объединяет повторно используемую операцию пересчёта очереди для foreground и worker; `ReminderCoordinator` наблюдает за изменениями данных в процессе приложения. Отдельные классы use case для каждого getter не создаются: [domain layer в Android](https://developer.android.com/topic/architecture/domain-layer) вводится при необходимости сложной или повторно используемой логики.

Имена классов `com.bmstu.iu3.core.data.ReminderWorker`, `ReminderReceiver` и `RestoreRemindersReceiver` сохранены внутри нового модуля уведомлений. WorkManager и AlarmManager сохраняют эти имена, поэтому их переименование нарушило бы уже поставленные задачи. Остальной код уведомлений находится в пакете `core.notifications`. Имена очередей, channel, Intent extras, DataStore и файла фото также сохранены.

## Состояние фичей и Compose

`AppViewModel` отвечает только за первоначальную загрузку, выбор между онбордингом и основной навигацией и обновление данных при возвращении в приложение. Он не сохраняет профиль, не импортирует фото, не обслуживает поиск или настройки фичей.

В feature-модулях находятся собственные ViewModel. Поиск хранит запрос через `SavedStateHandle`, готовит результаты и предложения вне композиции. Главная готовит оставшиеся занятия и афишу. Расписание получает занятия и группы через свою ViewModel. Преподаватели владеют поиском по каталогу и подготовкой карточки, курсы — подбором дисциплин и планов. Профиль готовит настройки и предварительный список уведомлений. Общие расчёты, используемые фичами и фоновыми задачами, остаются в `core:model`.

ViewModel создаются через `hiltViewModel` внутри контента `NavEntry`. `rememberViewModelStoreNavEntryDecorator` задаёт им владельца: разные экземпляры перехода «курс → преподаватель → курс» не разделяют одну ViewModel. У учебного плана собственная `StudyPlanViewModel`; аргументы передаются через assisted factory, выбор программы и семестра хранится в `SavedStateHandle`. Это соответствует [Nav3 recipe passing arguments](https://github.com/android/nav3-recipes/tree/main/app/src/main/java/com/example/nav3recipes/passingarguments/viewmodels/hilt).

UI получает состояние и callbacks. Состояние самих элементов — pager, прокрутка, раскрытие карточек, активный диалог и фокус — остаётся рядом с элементом и сохраняется через штатные saver. У расписания единственным источником выбранной даты остаётся дневной PagerState: смена недели мгновенно переводит его на тот же день недели. Перенос этого состояния во второе независимое поле ViewModel создал бы рассинхронизацию жеста и выделения.

Такое распределение следует [state hoisting в Compose](https://developer.android.com/develop/ui/compose/state-hoisting). Статический экран выпускников не получает пустую ViewModel: его действия — переходы и открытие внешних приложений, собственного загружаемого состояния у него нет. Форматирование подписей и сопоставление типов с цветами остаются UI-логикой компонентов.

Пакеты фичей: `navigation` — entrypoints; `presentation` — ViewModel и UI state; `ui` — экраны; `ui.components` — компоненты; `ui.format` — отображение значений; `domain` — независимые алгоритмы фичи; `data` — локальные источники её конфигурации, например поискового словаря. `ui.state` содержит состояния самих элементов интерфейса. Экран — первая функция своего файла. Верхнеуровневые классы имеют отдельные файлы; вложенные варианты закрытых sealed-типов остаются частью своего типа.

## Строки, коды и оформление

Для закрытых состояний используются enum/sealed-типы: экран, аргументы перехода, вид результата поиска, статус события и вид напоминания. Открытые коды ответов представлены сериализуемыми value class с известными значениями: новый код сервера сохраняется как строка, а не ломает декодирование всего каталога. JSON-представление и сохранённые наборы настроек остаются строковыми.

UI-тексты и поисковые синонимы находятся в ресурсах feature-модулей. Пути и ключи хранения принадлежат источникам, регулярные выражения и словари — алгоритмам, ID изображений — `ImageAssets`, публичные ссылки — именованной конфигурации. Пустые строки, пунктуация и значения самих объявленных кодов не обёрнуты в искусственные константы.

Форматирование выполняется штатным Android Studio `format.sh` с factory defaults. Параметры объявлений с числом больше двух размещаются по одному на строке. Вызовы локальных API используют именованные аргументы; особенно это касается строк, флагов, маршрутов и UI callbacks. Код не полагается на оптимизацию импортов как побочный эффект форматера.

При рефакторинге применены [navigation-3](https://github.com/android/skills/tree/main/navigation/navigation-3), [adaptive](https://github.com/android/skills/tree/main/jetpack-compose/adaptive) и [jetpack-compose-performance](https://github.com/android/skills/tree/main/jetpack-compose/jetpack-compose-performance). Динамические lazy-коллекции получили строковые ключи по идентичности содержимого и `contentType`. Чтение анимируемого угла перенесено в `graphicsLayer`; размеры портретов рассчитываются при измерении. Это статические изменения кода, а не измеренный результат производительности. Подтверждённые сборки и ручные сценарии фиксируются в [verification.md](verification.md).

## Завершение пользовательских записей

Записи профиля, настроек, истории и импорт фото выполняются в переданном через DI scope приложения. Закрытие NavEntry отменяет ожидание UI, но не уже принятую запись. Репозиторий сериализует изменения через `Mutex`; запуск `UNDISPATCHED` сохраняет порядок принятия операций до первой приостановки. Сброс завершает удаление фото и после перехода приложения к онбордингу. `AtomicFile` защищает прежний файл фото при неудачной записи.

Это применение [рекомендаций Android по корутинам](https://developer.android.com/kotlin/coroutines/coroutines-best-practices): работа, нужная вне текущего экрана, получает внешний scope. Ошибки возвращаются активному вызывающему коду, а фичи показывают состояние неудачной записи; `CancellationException` распространяется отдельно. Процесс приложения всё ещё может быть завершён системой: для долгих обязательных фоновых операций предназначен WorkManager.

Wildcard-импорты запрещены; проект использует явные импорты.
